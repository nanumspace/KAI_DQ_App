# 파일럿 키트

실제 병원 데이터로 Quality Validator 를 처음 돌리는 파일럿을 위한 묶음입니다. 지금까지 규칙은 가상데이터로만 검증했습니다. 파일럿이 답해야 할 질문은 하나입니다 — **실제 데이터에서 규칙이 어떻게 우는가.** 오탐이 어디서 나는지, 명세가 현장과 어디서 어긋나는지, 입력 준비의 어느 단계가 막히는지.

| 파일 | 용도 |
|---|---|
| [`README.md`](README.md) (이 문서) | 참여 기관이 할 일, 보내는 것과 보내지 않는 것, 일정 |
| [`feedback.md`](feedback.md) | 기관이 채워 보내는 피드백 양식 |
| [`feedback_rules.csv`](feedback_rules.csv) | 규칙 단위 이의를 표로 적을 때 쓰는 헤더 |
| [`aggregate.py`](aggregate.py) | 중앙이 여러 기관의 `submission.json` 을 모아 규칙별로 집계하는 도구 |
| [`review/`](review/) | 임상 검토 묶음: 병리 보고서 조건부 필수 10건, v1→v2 미승격 필드 575건 (`build_review.py` 가 만듦) |

## 참여 기관이 할 일

1. **설치.** [Releases](../../../releases)에서 설치 파일을 받아 설치합니다. → [설명서 1장](../manual/01-install.md)
2. **동작 확인.** 같은 페이지의 견본 데이터 zip 하나(예: `SampleData-<버전>-LUNG_CANCER-dirty.zip`)를 넣어 README.txt 의 참조 결과와 위반 건수가 같은지 봅니다. 다르면 설치 문제이니 먼저 알려 주세요.
3. **EHR 추출본 준비.** OMOP CDM 표 14개를 CSV 로 내보냅니다. 컬럼은 **입력 양식 내려받기 → 컬럼 명세서**를 따릅니다. 사례가 없는 표(예: DEATH)도 헤더만 있는 파일로 둡니다. → [설명서 2장](../manual/02-input.md)
4. **서식 준비.** **입력 양식 내려받기 → 서식 양식**으로 받은 빈 서식을 채웁니다. 코드는 README.txt 의 목록에서 고릅니다. 파일럿에서는 **서식 전부를 채우지 않아도 됩니다** — 병리 보고서·바이오마커·코호트 인덱스처럼 준비된 것부터.
5. **서식 변환.** 앱의 **서식 변환** 화면에 서식 폴더를 넣습니다. '확인할 점'에 나온 것은 서식을 고쳐 다시 변환합니다. → [설명서 3장](../manual/03-run.md)
6. **검증 실행.** EHR 추출본 폴더와 서식 변환 결과 폴더를 **함께** 넣고 실행합니다. 검증 실행일은 **데이터를 뽑은 날**로 맞춥니다.
7. **결과 보기.** 위반이 많이 나오는 것이 정상입니다. 형식 문제(컬럼 구성·타입)를 먼저 고치고 한 번 더 돌린 뒤, 남는 것을 봅니다.
8. **보내기.** 아래 "보내는 것"을 보내 주세요.

처음 한 번은 3~6 단계에 걸린 시간을 적어 주시면 다음 기관의 안내에 씁니다.

## 보내는 것

| 무엇 | 어디서 | 왜 |
|---|---|---|
| `submission.json` | 실행 폴더 (결과 화면의 **실행 폴더 열기**) | 규칙별 통과·실패·위반 건수, 표별 행 수, 입력 정규화 건수. **환자 단위 정보 없음** |
| `feedback.md` (채운 것) | 이 폴더의 양식 | 오탐이라고 보는 규칙, 명세가 현장과 다른 곳, 값 집합에 없는 코드, 준비하며 막힌 곳 |
| `feedback_rules.csv` (선택) | 이 폴더의 양식 | 규칙 단위 이의가 많을 때 표로 |

두 번 돌렸다면(형식 문제 고치기 전·후) `submission.json` 두 개를 모두 보내 주세요. 파일 이름에 실행 ID 가 들어 있어 구분됩니다.

## 보내지 않는 것

- `findings.csv`, **오류 현황 조회**에서 내보낸 CSV — 환자 ID 와 값이 들어 있습니다.
- 실행 폴더의 `input/` — 정규화된 입력 데이터 원본입니다.
- 서식 CSV, EHR 추출본 — 데이터 자체입니다.
- **결과 폴더로 내보내기**로 만든 폴더째 — 위 `findings.csv` 가 들어 있습니다.

`submission.json` 의 `label`(실행 이름)은 그대로 실립니다. 환자를 알아볼 수 있는 말을 넣지 않습니다.

규칙 이의를 적을 때 위반 행의 **값은 필요 없습니다.** "규칙 SEMV-COM-006 이 응급실 방문에서 계속 걸린다, 우리는 응급실 방문 종료일을 입원 전환 시점으로 적는다" 정도면 충분합니다.

## 중앙이 돌려주는 것

- 기관별 결과 요약과, 여러 기관에서 함께 우는 규칙 목록(`aggregate.py` 산출물).
- 이의가 받아들여진 규칙의 수정 내역과 다음 판 앱.
- 값 집합에 보탠 코드.

## 일정 (안)

| 주 | 할 일 |
|---|---|
| 1 | 설치, 견본 데이터로 동작 확인, EHR 추출본 준비 시작 |
| 2–3 | EHR 추출본 완성, 서식 일부 채우기, 첫 실행 |
| 4 | 형식 문제 고친 뒤 두 번째 실행, `submission.json` 과 피드백 송부 |
| 5 | 중앙 집계와 규칙 수정, 결과 회신 |

## 파일럿에서 알고 싶은 것 (중앙의 체크리스트)

- [ ] 설치가 병원 PC(망 분리·보안 정책)에서 되는가
- [ ] EHR 추출본 준비에 며칠 걸리는가, 어느 표가 어려운가
- [ ] 내보내기 흔적(인코딩·대문자·NULL·`.0`·구분자)이 실제로 어떤 모양으로 오는가 — `submission.json` 의 `normalization`
- [ ] 서식을 채우는 데 코드 목록이 충분한가, 어느 값 집합이 모자라는가
- [ ] 규칙 가운데 **모든 기관에서 우는 것** — 규칙이나 명세의 문제일 가능성이 크다
- [ ] 규칙 가운데 **한 기관에서만 우는 것** — 그 기관의 내보내기나 관행일 가능성이 크다
- [ ] 실행 시간과 메모리 (2,000명 규모까지는 확인했다)
- [ ] 보고서가 담당자에게 읽히는가, 조치 안내가 도움이 되는가

## 임상 검토 (파일럿과 나란히)

`review/` 의 두 표는 임상 검토자에게 따로 보냅니다.

- `pathology_conditional_review.xlsx` — PATHOLOGY_REPORT 컬럼 10개가 생검·수술 어느 보고서에 필수인지. 지금은 '둘 다'로 두어 규칙이 느슨합니다. 답이 오면 `spec/v2_row_kinds.py` 의 `NEEDS_REVIEW` 를 비우고 `applies` 에 옮깁니다.
- `legacy_fields_review.xlsx` — v1 컬럼 575개 중 v2 에 자리가 없는 것. '대응 없음' 83건과 '부분 일치' 149건만 보면 됩니다. 병원이 "이 항목 어디 갔나요" 물을 때의 답이기도 합니다.
